# ПУЛЬС.Кампус: описание процесса создания

## 1. Проблема и идея

Учебная жизнь студента обычно разрознена: расписание находится на одном сайте, оценки — в другой системе, справки оформляются через деканат, а новости теряются в чатах и почте. Сервис должен не копировать очереди сайтов, а собирать эти задачи в один понятный поток.

Мы выбрали **Bento-подход**, потому что он позволяет одновременно показать главное — ближайшую пару, академический пульс, заявки и уведомления. Интерактивные секции «Расписание», «Успеваемость», «Заявки» и «Уведомления» сохраняют контекст и требуют минимум переходов. Мобильный Tab Bar и адаптивность от 360 px обеспечивают управление одной рукой.

## 2. Технологический и ИИ-стек

- **GitHub Copilot Agent в PyCharm** — проектирование экранов, реализация Python-сервера, HTML/CSS/JavaScript, отладка и рефакторинг.

- **Интеграционный ассистент** — проверка подключения `/logo.png`, favicon, шапки, экранов входа, справок и AI-виджета.
- **Browser / HTTP-проверки** — ручная проверка сценариев и стандартный `python -m unittest`.

## 3. Эволюция проекта

### Этап 1. Базовый прототип

Сначала была собрана минимальная рабочая версия на чистом Python + SQLite. Реализованы вход, расписание, оценки, заявки и разделение кабинетов по пользователю. На этом этапе ассистенту был дан промпт создать прототип вместо статического макета и сохранить тестовые аккаунты.

Ключевой промпт: «Создай работающий личный кабинет студента: вход, расписание, успеваемость, заявки и уведомления. Данные должны храниться не на клиенте, а в SQLite; пароли хешировать».

### Этап 2. Дизайн-система

Следующая итерация перешла к Neo-Minimalism Bento UI. Были заданы светлая и тёмная темы, акцентное индиго, карточная сетка, скелетоны, микро-анимации и адаптивный Tab Bar.

Ключевой промпт: «Переделай интерфейс до уровня коммерческого продукта. Сохрани обязательные сценарии, но сделай главную экраном быстрого выбора: следующая пара, академический пульс, заявки и новости».

### Этап 3. Роли и отдельные сценарии

Для роли студента реализована зачетка и заявки, а для роли сотрудника — входящие заявки, смена статусов и публикация объявлений. Вход студента с пересдачей отличается данными от отличника.

Ключевой промпт: «Добавь три демо-аккаунта для жюри и роль staff с панелью управления заявками».

### Этап 4. Маскот и бренд

Рыжий пиксельный осьминог был встроен в favicon, навигацию, Login Hero, AI-виджет и бланк справки. Оригинал сохраняется как `logo.png`, а при сбое применяется SVG-fallback.

Ключевой промпт: «Используй реальный загруженный `logo.png` во всём интерфейсе и не заменяй оригинал сгенерированным изображением».

### Этап 5. Безопасность и деплой

Добавлены переменные окружения, Docker-конфигурация и автоматические HTTP-тесты. `.github/copilot-instructions.md` фиксирует правила для последующих изменений: не использовать реальные данные, защищать владельца заявки и сохранять единый бренд-маскот.

## 4. Архитектура входа и хранения данных

Пароль студента не хранится в SQLite открытым текстом. При создании аккаунта генерируется случайная соль и вычисляется PBKDF2-SHA256 с 120 000 итерациями:

```text
случайная соль + пароль -> PBKDF2-SHA256 -> соль$хеш
```

При входе рассчитывается новая производная по введённому паролю и сравнивается с сохранённым хешом через постоянное по времени сравнение `hmac.compare_digest`.

Сессия создается случайным payload и подписывается HMAC-SHA256 секретом `APP_SECRET`. Токен хранится в HttpOnly-cookie с `SameSite=Strict`. По умолчанию секрет создается случайно при старте сервера. Для постоянной работы за перезапусками рекомендуется задать переменную `APP_SECRET` из секретов хостинга.

Данные заявок запрашиваются по `user_id` текущего пользователя. Эндпоинты студента проверяют владельца до выдачи или изменения заявки. Эндпоинт деканата доступен только для пользователя с ролью `staff`. Тестовый сценарий дополнительно проверяет чужую заявку под `alexey` и изменение статуса как студента.

База содержит только вымышленные имена, направления и записи. Настоящие аккаунты вузов не подключаются.

## 5. Структура проекта

- `app.py` — HTTP-сервер, SQLite, вход, API ролей, сессии, хеши и переменные окружения.
- `index.html` — интерфейс входа, навигации и AI-виджета.
- `styles.css` — дизайн-система, темы, адаптивность и стили маскота.
- `app.js` — переключение кабинетов, формы, трекеры, модальные окна и клиентская логика.
- `logo.png` — оригинальный PNG-маскот проекта.
- `logo-fallback.svg` — резервная SVG-иконка при недоступности PNG.
- `Dockerfile` — контейнерный деплой.
- `tests/test_security_and_flow.py` — HTTP и security regression-тесты.
- `.github/copilot-instructions.md` — постоянные правила для ИИ-ассистентов.

## 6. Этапы ручной работы

После генерации ИИ-кода ручная работа включила:

1. Проверку HTTP-маршрутов и тестовых аккаунтов.
2. Исправление структуры SQLite при добавлении ролей и комментариев методиста.
3. Проверку мобильной сетки на ширине 360 px.
4. Замечание и замену сгенерированного логотипа на загруженный пользователем оригинал.
5. Проверку ошибок ИИ в синтаксисе JavaScript/Python.
6. Проверку загрузки favicon и статических PNG/SVG.
7. Запуск security-тестов и исправление маршрута проверки владельца заявки.
